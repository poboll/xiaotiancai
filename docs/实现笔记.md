## 二、数据是怎么来的：build_library.py

扫描 `抖音源/` 和 `小红书源/` 里每个带 `info.json` 的文件夹，产出 `data/library.js` 和缩略图：

- `info.json` 是下载工具留下的元数据（标题、发布时间、统计、媒体清单）
- 图文作品：`images[]` 逐张生成 640px webp 缩略图（`thumbs/<hash>/01.webp`），首图当封面
- 视频作品：`make_poster()` 用 ffmpeg 抽帧当封面；有 `video_web.mp4` 就优先用它（原片超 GitHub 单文件 100MB 上限）
- 瓦片宽高比用封面实际尺寸算，横竖屏混排不会变形
- 置顶顺序写在脚本的 `PINNED_ORDER`（按 `aweme_id`）

**封面管线（2026-10-25 重修）**：两个纪录片的设计封面是从抖音拿的全尺寸大图（1MB+），直接进首页瓦片太狠。现在管线是：

| 用途 | 文件 | 尺寸 |
|---|---|---|
| 瓦片 | `cover.webp` | 640px，q74 |
| 详情页 | `poster.jpg` | ≤1120px（显示容器 560px，覆盖 2x 屏），q88 渐进式 |

`library.js` 里视频作品多一个 `coverThumb` 字段，`app.js` 瓦片优先用它。**注意**：`thumbs/<hash>/` 的 hash 是文件夹相对路径的 md5——目录改名（比如整体挪进 `抖音源/`）会让 hash 变，旧封面不会跟过去，`make_poster()` 会重新抽帧。当年就这么丢过两张设计封面，后来从 git 历史里捞回来的。**搬目录前先想一下封面。**

## 三、小红书原图通道（最值得留的一段）

这一节是整个项目里最值钱的踩坑记录，代码化成果在 [video-parse](https://github.com/poboll/video-parse) 的 `platforms/xiaohongshu.py`。

### 1. 下载工具

Gitee 上的 [`hnxyy/xhs-downloader`](https://gitee.com/hnxyy/xhs-downloader)，Go 写的，go-rod 驱动 Chrome，读页面 `window.__INITIAL_STATE__` 拿数据，绕开 x-s / x-t 签名那套。

### 2. 游客只能看 31 篇，登录才有 80 篇

未登录状态下小红书主页只吐 31 篇笔记，滚到底就没了。扫码登录一次（登录态持久化在 `~/.xhs-dl/browser-data`），重跑，80 篇全量到手。

### 3. 网页端给的是缩图，不是原图

工具默认拿网页端签名 URL：

```
https://sns-webpic-qc.xhscdn.com/1040g2sg31.../{fileId}!nd_dft_wgth_webp_3
```

带签名、带「配方」，服务端按配方决定回多大的图——**1080 到 1439 宽之间的 webp**。改后缀、改参数一律 403。第三方解析能拿到 1703×2271，差了一截。

### 4. 突破口：抓包看去水印小程序

用户给了一个去水印小程序的 HAR 抓包（36MB，248 个请求）。翻下来发现小程序后端是 `www.async-dev.fun`，图片请求长这样：

```
https://ci.xiaohongshu.com/{fileId}?imageView2/2/w/0/format/png
```

三个关键点：

- **`ci.xiaohongshu.com` 是另一个 CDN**，不走网页端那套签名
- **`w/0` 是不缩放**，服务端按原尺寸给
- **`format/png` 是无损转出**——裸链默认返回 HEIC 原片，指定 png 才转成 PNG

小程序下的文件和第三方解析下的文件**字节数完全一致**，确认同一个源。

### 5. fileId 从哪来

```
entry.note.noteDetailMap[noteId].note.imageList[].fileId
```

`imageList` 每一项的 `width`/`height` **就是原图尺寸**（比如 2560×1922）；网页端 URL 里的尺寸是服务端另外算的，两者不是一回事。

### 6. 给工具打补丁

| 文件 | 改动 |
|---|---|
| `internal/xhs/types.go` | `Image` 结构加 `FileId` 字段 |
| `internal/xhs/note.go` | 解析时把 `fileId` 带出来 |
| `internal/cli/common.go` | 图片任务优先拼 `ci.xiaohongshu.com` 原图地址，网页 URL 降级成 fallback |

### 7. 扩展名 bug：Content-Type 会骗人

补丁跑通后文件扩展名全是 `.jfif`/`.jpg`，内容其实是 PNG。两个坑叠一起：

- Go 的 `mime.ExtensionsByType("image/png")` 在部分系统上返回 `.jfif`
- **直连（不走代理）时 `ci.xiaohongshu.com` 把 PNG 内容标成 `Content-Type: image/jpeg`**

所以不能信响应头，改成读**文件头魔术字节**判格式（`sniffExt`）。这一下根治。

### 8. 结果

360 张原图全量重下，1.5GB，尺寸 1440×1920 / 1920×2560 / 1706×2560 / 2560×1922 等，`info.json` 里记的尺寸和实际文件零误差。

## 四、抖音清晰度实测结论

拿接口原始数据逐条实测的，不是看尺寸猜。

### 图片：尺寸是原图，质量档是 q75

| 字段 | 模板 | 特征 |
|---|---|---|
| `images[].url_list[0]` | `tplv-dy-aweme-images:q75.webp` | **无水印、不带缩放参数** ← 用的是这个 |
| `images[].download_url_list[0]` | `tplv-dy-water-v2:<水印>:W:H.webp` | 带水印，且缩到 API 声明的尺寸 |

两个关键实测：

1. **`q75` 模板没有缩放参数，服务端返回的就是原图分辨率。** 如 `aweme_id=7509483903486446905`，API 声明 1440×1920，实际取到 **2160×2880**；本地文件和链接返回字节级一致。所以 `info.json` 里记的 `width`/`height` 是低一档的声明值。
2. **想换更高档不行。** 模板改 `q90`/`q100`/去掉模板全部 **403**——URL 的 `x-signature` 和模板绑定，改一个字符签名就失效。接口里也没提供别的无水印档位。

**结论：尺寸上早就拿到原图了，唯一残留的是 q75 这个有损压缩档，抖音不提供更高的无水印档位。**

### 视频：最高档

`video.bit_rate` 是按码率降序的档位表。下载逻辑优先 `download_addr.url_list`，否则展平所有 `bit_rate[].play_addr.url_list` 取第一条（最高档）。实测两部纪录片都是 3840×2160 HEVC（4.45 / 3.20 Mbps），和档位表顶部条目对得上。

## 五、体积与清晰度的账：WebP 与 LFS

### 图片：全分辨率 WebP，PNG 原片留本地

PNG 原图单张 4–7MB，360 张 1.5GB。直接进 git 仓库会涨到 1.8GB——clone 慢，站点每点开一张图都要加载 4MB+。

`xhs_png_to_webp.py` 转成**同分辨率 WebP**（q92, method 6）：

- 像素数一点没变，还是 1706×2560 / 2560×1922
- 体积降到 PNG 的 **16%** 左右（1.5GB → 210MB）
- q92 对照片视觉无损，损失只在发丝、远处树叶这类极高频细节里

PNG 原片没删，移到各作品 `原图/` 子目录，`.gitignore` 挡掉只留本地。抖音那边的图下载下来就是 webp，不用转。

### 视频：只有 mp4 走 LFS

`.gitattributes` 只让 mp4 走 LFS。mp4 是二进制 git 压不动，且原片可能超 100MB 上限。进 LFS 的视频一共 110MB 左右。

### 为什么图片不走 LFS（算过账的）

GitHub Pro 的 LFS 配额是 **2GB 存储 + 2GB 月带宽**。1.5GB 原图走 LFS：

- 存储一口吃掉 75%，基本没余量
- 更致命的是**带宽**——Pages 每次自动部署都要 `actions/checkout(lfs:true)` 拉一遍，**一次部署就是 1.5GB，一个月只能部署一次**

所以图片走普通 git + WebP，只有视频走 LFS。

### 4K 母版留本地

两部纪录片 4K 母版（174MB / 163MB）超 GitHub 单文件 100MB 上限，`.gitignore` 排掉；进仓库的是压过的 `video_web.mp4`（1080p，35–52MB）。

### 2026-10-24 补：信件页视频压缩

`media/nvzhu.mp4` 原 21MB（720p 2Mbps）。页面显示宽度只有 640px，压成 **960×540 CRF30 + AAC 64k 单声道 + faststart → 7.1MB**，抽帧对比画质可接受。视频一律加 `+faststart`（moov 前置），否则要等整文件下完才能播。

## 六、双平台去重

同一部作品两边都发，但选图和标题不一定一样，不能按标题判重。`dedupe_xhs.py`：

1. 对小红书首图和抖音封面算 **ahash**（16×16 平均哈希，256 bit）
2. 距离 ≤ 8 的进候选
3. 候选再按**全图重叠率 ≥ 60%** 最终判定
4. 标题相似度做 tiebreak

结果写在 `scripts/dupe_map.json`，12 部双平台作品。`build_library.py` 消费它：命中的小红书作品不单列，合并进抖音条目，渠道改「双平台」，附 `xhsLink`。重复的 12 份小红书媒体（355MB）由脚本自动写 `.gitignore` 挡掉，只留 `info.json`。

> 2026-10-24：首页瓦片上的「小红书/双平台」角标已按用户要求去掉，渠道数据只留在漏斗筛选里。

## 八、字体：为什么 iPad 上是宋体

**坑**：CSS 字体栈写 `"Songti SC", ... serif`，macOS 正常，iPad 打开变苹方——**iOS/iPadOS 没有 Songti SC 系统字体**，逐级 fallback 落到 sans。

**解法**：从 Mac 系统字体库 `/System/Library/Fonts/Supplemental/Songti.ttc` 抽出 `fontNumber=6`（Songti SC Regular），按**全站实际用字**（含 `library.js` 里 128 部作品的标题，共约 1260 字）子集化成 woff2（**403KB**），自托管到 `assets/fonts/`，`@font-face` 命名 `Songti SC Web` 放在 `--serif` 栈首位。全设备（含 Windows/安卓）宋体一致。

```bash
# 重新生成字体子集（换字库内容后）
pip install fonttools brotli
python3 - <<'PY'
from fontTools.ttLib import TTFont
from fontTools import subset
chars = "..."  # 从各 HTML + library.js 收集用字
opts = subset.Options(); opts.flavor = "woff2"; opts.with_zopfli = True
ss = subset.Subsetter(options=opts); ss.populate(text=chars)
f = TTFont("/System/Library/Fonts/Supplemental/Songti.ttc", fontNumber=6)
ss.subset(f); f.save("assets/fonts/SongtiSC-subset.woff2")
PY
```

**踩过的返工**：用户一度想用手写体（子涵 104 号书信体）做信件页，上了两天又嫌不好看全部撤掉。**换字体这种全局视觉改动，先做一页给用户看，别全站铺开。**

**缓存**：iOS Safari 对 CSS 缓存很狠，改完样式用户端不刷新。给 `site.css` 链接加版本号（`?v=5`），改一次提一次。

## 九、加载性能

### 已做的

| 手段 | 状态 | 效果 |
|---|---|---|
| 图片 WebP | ✅ | 全站图片皆 webp，缩略图 640px q74 |
| 懒加载 | ✅ | 瓦片/插图/剪辑片段全 `loading="lazy" decoding="async"` |
| gzip | ✅ 自动 | GitHub Pages 服务端压缩：CSS 28KB→7KB，JS 10KB→3.6KB |
| 视频不预载 | ✅ | 详情页视频点播放才加载；信件页视频 `preload="metadata"` |
| 字体子集 | ✅ | 403KB 按需子集，`font-display: swap` |
| 封面缩略图 | ✅ | 设计封面 1MB+ → 瓦片 73KB |

###  CDN 的结论（2026-10-25 评估）

用户问能不能上 jsDelivr 之类的 CDN。**结论：没必要，也不一定更快。**

- jsDelivr 可以代理 GitHub 仓库文件（`cdn.jsdelivr.net/gh/poboll/xiaotiancai@main/...`），但和 Pages 是同源文件，没有额外节点优势
- 国内访问 jsDelivr 不稳定，时好时坏；Pages 走 Fastly 也一般，但至少是单一依赖、没有第三方 cookies/隐私问题
- 站点本身已经够轻（首屏文字 + 几十 KB 的图），**真正的瓶颈从来不是 CDN，是别把大文件放进首屏**
- 如果哪天要迁：对象存储 + CDN（七牛/又拍/阿里 OSS）是国内正路，但那是另一个工程了。**在作品量和访客量起来之前，Pages 够用。**

### 文字优化

- 宋体子集 + `text-rendering: optimizeLegibility`，长文阅读用 1.9–2.1 行高、两端对齐
- 信件页正文 18px、行高 2.02，评论 15.5px——**只放大书信内容，别的地方不放大**（用户明确要求）
- 瓦片标题两行截断，meta 用小字，视觉重量在图上不在字上

## 十、部署与域名

推到 `main` 自动部署。workflow 先跑 `build_library.py` 再上传；checkout 带 `lfs: true`，视频实体才会被拉下来。

自定义域名 `xtc.caiths.com` 走 Cloudflare：

- DNS 加 `CNAME xtc → poboll.github.io`，**代理状态关掉**（灰色云，DNS only）。开着橙云 GitHub 签不出证书
- 仓库 Pages 设置填 `xtc.caiths.com`，等证书签发（几分钟到半小时）
- 证书好了再勾 `Enforce HTTPS`

**推送卡死的排查**：本地代理（Clash 7897）抽风时 `git push` 会挂住——`git-remote-https` 进程 idle、连接 ESTABLISHED 无数据。杀掉进程，`GIT_TRACE_CURL=1 git push origin main` 重试即可。

**额度**（GitHub Pro，2026-10 查）：仓库 551MB / Pages 软限 1GB；10 月构建 14 次约 40 分钟 / 月度 3000 分钟；带宽软限 100GB/月远未到。**大文件进仓库前先压缩**，每压一次都是给额度续命。

**视频压网页版**（原片超 100MB 时）：

```bash
ffmpeg -i video.mp4 -vf scale=1920:-2 -c:v libx264 -preset medium \
       -b:v 900k -c:a aac -b:a 96k -movflags +faststart video_web.mp4
```

`build_library.py` 会优先用 `video_web.mp4`。
